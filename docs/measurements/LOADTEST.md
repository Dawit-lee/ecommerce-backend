# S-Com HTTP 부하 테스트 (상품 조회)

측정일: 2026-11-10 · 브랜치: `claude/loadtest-tps-d4ab16` · 원본: [`loadtest-raw/`](loadtest-raw/) · 실행 방법: [`loadtest/README.md`](../../loadtest/README.md)

`RESULT.md`의 기존 수치는 서비스 메서드를 직접 호출해서 잰 값이다. 이 문서의 수치는 실제 서버에 HTTP 요청을 보내 측정했으므로 JWT 필터, 직렬화, 네트워크 시간까지 포함된다.

## 요약

같은 머신, 같은 자원 제한, 같은 데이터(상품 100만 건), 같은 시나리오에서 측정했다. VU당 60초씩 돌렸다.

| 단계 | 바꾼 것 | 최대 TPS (해당 VU) | VU 50 TPS | VU 50 p95 | 에러율 |
|---|---|---:|---:|---:|---:|
| 0. 개선 전 | – | 13.0 (VU 1) | 8.0 | 8,495.6 ms | 0% |
| (시도) 풀 10 → 30 | Hikari `maximumPoolSize` | – | 6.8 | 17,086.3 ms | 0% |
| 1. 인덱스 | pg_trgm GIN, `price`, `category_id` | 38.1 (VU 1) | 34.3 | 1,815.9 ms | 0% |
| 2. count 캐시 | 페이지 조회는 `Slice`, 총개수는 30초 캐시 | 771.5 (VU 200) | 736.5 | 177.2 ms | 0% |
| 3. N+1 제거 | `Product.category`·`Product.user`를 LAZY로 | 1,525.5 (VU 5) | 1,016.8 | 108.4 ms | 0% |
| 3. 재측정 | 코드 동일, 한 번 더 실행 | 1,560.1 (VU 5) | 1,188.0 | 100.3 ms | 0% |

- 개선 전과 후를 VU 50에서 비교하면 TPS는 **8.0에서 1,016.8(재측정 1,188.0)** 로 늘었고, p95는 **8,495.6ms에서 108.4ms(재측정 100.3ms)** 로 줄었다.
- 같은 코드를 두 번 측정했을 때 차이는 VU 5에서 2.3%, VU 50에서 16.8%, VU 100에서 15.2%였다. 그래서 TPS는 한 자리 정밀도로 믿기 어렵고 **대략 1,000~1,200 TPS 수준**으로 읽어야 한다.

## 시나리오

[`loadtest/read.js`](../../loadtest/read.js)는 모두 `GET /api/public/products`(프런트가 쓰는 엔드포인트) 호출이고, 요청 비율은 다음과 같다.

| 이름 | 비율 | 요청 |
|---|---:|---|
| list | 40% | `?pageNumber=0..99` (기본 정렬 `productId`) |
| category | 20% | `?category=Category-001..050&pageNumber=0..9` |
| keyword | 20% | `?keyword=<명사 10종>&pageNumber=0..9` |
| price_sort | 20% | `?sortBy=price&sortOrder=desc&pageNumber=0..99` |

- 닫힌 모델(`constant-vus`)에 think time 0으로 돌렸다. 그래서 VU는 동시 사용자 수가 아니라 **동시에 처리 중인 요청 수**에 가깝다.
- VU 단계마다 60초씩 실행했다. 단계 전체를 시작하기 전에 워밍업으로 VU 5에서 15초를 돌렸고, 이 결과는 버렸다.
- **주문 흐름은 측정하지 않았다.** 이번에는 읽기 경로만 다뤘다.

## 탐지 → 원인 → 개선

자원 사용률은 `docker stats`를 4초 간격으로 찍은 값을 VU 50 구간 평균으로 낸 것이다. 100%가 CPU 1코어이고, 두 컨테이너 모두 한도는 200%다.

| 단계 | 앱 CPU | DB CPU | Hikari 대기 최대 | 요청당 SQL 수 | DB 실행 시간 중 count 쿼리 비율 |
|---|---:|---:|---:|---:|---:|
| 0. 개선 전 | 7% | 203% | 40 | 약 18 | 68.4% |
| 1. 인덱스 | 8% | 201% | 40 | 약 18 | 95.4% (전체 count 하나가 78.4%) |
| 2. count 캐시 | 104% | 207% | 40 | 약 18 | 1.5% |
| 3. N+1 제거 | 89% | 205% | 40 | 1 | 1.0% |

(요청당 SQL 수 = VU 50 구간 `pg_stat_statements` 상위 15개 쿼리의 호출 수 합 ÷ k6 요청 수. `BEGIN`은 제외했다. 원본: `loadtest-raw/<단계>/pgss_vus50.txt`, `stats_vus50.csv`, `prom_vus50.txt`)

### 0 → 1: 인덱스

- **탐지.** VU 1에서 이미 TPS가 13이었고 VU 5에서는 5.1로 떨어졌다. 그동안 DB CPU는 200% 근처에 붙어 있었고 앱 CPU는 7~20%였다. 앱이 아니라 DB가 병목이다.
- **원인.** `pg_stat_statements`의 VU 50 구간 DB 실행 시간 기준 상위 항목은 `lower(product_name) like '%kw%'` count 쿼리(32.8%)와 필터 없는 `count(*)`(25.2%)였다. 단건 실행 플랜([`loadtest-raw/baseline/explain.txt`](loadtest-raw/baseline/explain.txt))은 다음과 같다.
  - 키워드 count: `Parallel Seq Scan` 100만 건, **450.9ms**
  - 키워드 페이지: `Parallel Seq Scan` + top-N sort, 129.5ms
  - 카테고리 count: `products` 전체 `Parallel Seq Scan`, 81.1ms. PostgreSQL은 FK 컬럼(`category_id`)에 인덱스를 자동으로 만들지 않는다
  - 가격 정렬 페이지: `Parallel Seq Scan` + top-N sort, 64.9ms
- **개선.** [`schema.sql`](../../src/main/resources/schema.sql)에 `pg_trgm` GIN(`lower(product_name)`), `price`, `category_id` 인덱스를 추가했다. 앱이 기동할 때 Hibernate DDL 다음에 실행된다. 단건 실행 시간은 다음처럼 바뀌었다([`loadtest-raw/step1_indexes/explain.txt`](loadtest-raw/step1_indexes/explain.txt)).
  - 키워드 count: 450.9 → **25.2ms** (Bitmap Index Scan)
  - 카테고리 count: 81.1 → **3.5ms**
  - 가격 정렬 페이지: 64.9 → **0.5ms** (Index Scan Backward)
- **결과.** VU 50 기준 TPS 8.0 → 34.3, p95 8,495.6 → 1,815.9ms.

### (효과 없던 시도) Hikari 풀 10 → 30

Hikari 대기가 최대 40건까지 쌓여서 풀 부족을 의심했다. 하지만 DB CPU가 이미 포화였으므로, 커넥션을 늘리면 같은 2코어를 더 많은 쿼리가 나눠 쓰게 될 뿐이다. 실제로 VU 25는 6.7 → 7.9 TPS로 비슷했고, VU 50은 8.0 → 6.8 TPS로 줄었으며 p95는 8,495.6 → **17,086.3ms로 나빠졌다**. 풀은 기본값 10으로 되돌렸다.

### 1 → 2: 매 요청마다 도는 count 쿼리

- **탐지.** 인덱스를 넣은 뒤에도 DB CPU는 201%였고 TPS는 약 34에서 멈췄다.
- **원인.** 이제 DB 실행 시간의 95.4%가 count 쿼리였다. 그중 필터 없는 `select count(product_id) from products where 1=1`가 **78.4%** 를 차지했다(평균 361ms, 단건 59~92ms). Spring Data의 `findAll(spec, pageable)`은 `Page`를 만들려고 **페이지를 요청할 때마다** 이 count를 실행한다. 100만 행을 세는 일은 인덱스로 줄일 수 없다(이미 `Parallel Index Only Scan`이다).
- **개선.** [`ProductServiceImpl.getAllProducts`](../../src/main/java/com/ecommerce/project/service/ProductServiceImpl.java)를 고쳤다.
  - 데이터는 `findBy(spec, q -> q.slice(pageable))`로 가져온다. count 없이 `pageSize + 1`건만 조회한다.
  - 총개수는 Caffeine 캐시(키는 키워드와 카테고리, 30초 TTL, 최대 10,000개)에서 읽는다.
  - 응답 형식(`totalElements`, `totalPages`, `lastPage`)은 그대로다. 테스트: [`ProductListingTest`](../../src/test/java/com/ecommerce/project/ProductListingTest.java)
- **결과.** VU 50 기준 TPS 34.3 → 736.5, p95 1,815.9 → 177.2ms. 이때부터 앱 CPU가 약 100%로 올라왔다. DB가 덜 막히니 앱이 일을 하기 시작한 것이다.
- **대가.** `totalElements`가 상품 등록이나 삭제 후 최대 30초까지 실제와 다를 수 있다.

### 2 → 3: N+1 (`Product.category`, `Product.user`가 EAGER)

- **탐지.** DB CPU는 여전히 207%였는데, 실행 시간이 가장 큰 쿼리들은 이미 수 ms 수준이었다. 대신 호출 횟수가 컸다. VU 50 구간 1분 동안 요청 44,285건에 대해 `users` 조회와 `categories` 조회가 합쳐서 **769,857회**, 요청당 **17.4회** 실행됐다.
- **원인.** `@ManyToOne`의 기본값은 EAGER다. 그래서 상품 10건을 읽으면 판매자(`users` + `carts` + `roles` 조인)와 카테고리를 상품마다 따로 조회했다. 이 결과는 `ProductDTO`에 쓰이지도 않는다. 쿼리 하나의 실행 시간은 0.01~0.03ms라서 `pg_stat_statements`의 시간 순위에는 거의 나타나지 않는다(DB 실행 시간의 약 3.6%). 하지만 쿼리마다 네트워크 왕복, 파싱·바인드, 커넥션 점유 시간이 든다.
- **개선.** [`Product`](../../src/main/java/com/ecommerce/project/model/Product.java)의 두 연관을 `fetch = LAZY`로 바꾸고, Lombok `toString`에서 제외해서 지연 로딩이 우연히 일어나지 않게 했다. 요청당 SQL 수는 약 18에서 **1**로 줄었다. 캐시가 비어 있을 때는 count가 하나 더 나간다.
- **결과.** VU 50 기준 TPS 736.5 → 1,016.8(재측정 1,188.0), p95 177.2 → 108.4ms(재측정 100.3ms).
- **해석의 한계.** `pg_stat_statements` 기준으로 요청당 DB 실행 시간은 5.87ms에서 5.64ms로 거의 그대로였다. 그러니 TPS가 오른 원인은 "쿼리 실행 시간 감소"가 아니라 "쿼리 왕복 17회 제거"로 추정된다. `pg_stat_statements`는 프로토콜 처리나 네트워크 비용을 실행 시간에 넣지 않기 때문이다. 이 추정은 따로 검증하지 않았다.

### 남은 병목 (고치지 않음)

3단계 이후에도 DB CPU는 205%로 포화였다. 이제 DB 실행 시간 1위는 **키워드 검색 페이지 쿼리**(VU 100 구간 평균 14.6ms)이고, 2위는 카테고리 페이지 쿼리(8.1ms)다. 플랜([`loadtest-raw/step3_lazy/explain.txt`](loadtest-raw/step3_lazy/explain.txt) 끝부분)을 보면 다음과 같다.

- `'%tent%'`는 trgm 인덱스에서 **33,357건**을 가져와 정렬한 뒤 11건만 쓴다(버퍼 16,315개, 21.96ms).
- 작은 카테고리는 PK 순서로 8,414건을 훑은 뒤 11건만 남긴다(4.48ms).

다음에 해볼 만한 방법은 `(category_id, product_id)` 복합 인덱스, 키워드 검색 범위를 줄이거나 전문 검색으로 바꾸는 것, keyset 페이지네이션이다. 이번에는 구현하지도 측정하지도 않았다.

## 한계 (해석할 때 반드시 같이 볼 것)

1. **부하기와 서버가 같은 머신이다.** k6(호스트)와 앱·DB(Docker VM)가 같은 M4 칩을 나눠 쓴다. 컨테이너는 각각 2코어로 제한했지만 k6 자체가 쓰는 CPU는 제한하지 않았다. 같은 Docker VM에서 다른 프로젝트 컨테이너(`env-license-app-*`, `sample-project-mysql`)도 켜져 있었다. 측정 시작 전 사용률은 각각 0~3%였다.
2. **절댓값보다 전후 비교가 의미 있다.** 운영 환경(EB와 RDS, 네트워크 지연 있음)에서는 측정하지 않았다. 앱과 DB가 같은 VM 안에 있어서 네트워크 왕복이 매우 짧다. 그래서 N+1 개선 효과는 운영에서 더 클 수도, 작을 수도 있다.
3. **count 캐시는 이 시나리오에 유리하다.** 필터 조합이 61가지(필터 없음 1, 카테고리 50, 키워드 10)뿐이라 캐시가 거의 항상 맞았다. VU 50 구간 1분 동안 count 쿼리는 122회 실행됐다. 실제 사용자는 키워드를 다양하게 입력하므로 적중률이 이보다 낮다. 그 경우 키워드 count(인덱스 사용 시 단건 25ms)가 다시 드러난다.
4. **실행 간 편차가 있다.** 같은 코드를 두 번 쟀을 때 VU 50에서 16.8% 차이가 났다. 단계별 측정은 VU마다 1회씩만 했다(3단계만 2회).
5. **3단계 첫 측정은 버렸다.** 첫 시도 도중 compose 스택 전체(앱·DB·Prometheus)가 외부 요인으로 종료됐다. 원인은 확인하지 못했다. 그 결과 VU 1 구간이 연결 거부로 99.58% 실패했고, 이 결과는 삭제한 뒤 다시 측정했다(데이터 볼륨은 그대로 유지됨).
6. **읽기 경로만 다뤘다.** 주문(쓰기)과 로그인, 장바구니는 측정하지 않았다. Stripe 호출도 이 시나리오에는 없다.
7. Grafana는 붙이지 않았다. 지표는 Prometheus API로 조회해서 `prom_vus*.txt`에 기록했다. `tomcat_threads_busy_threads`는 수집되지 않아서 빈 값으로 남았다.
